# ADR-004: 拒绝引入 Neo4j，坚持 PostgreSQL 单存储

**日期**: 2026-07-20
**更新**: 2026-08-04（补充不用图数据库的代价分析）

**状态**: 已接受

## 背景

在引入三阶段抽取（摘要→实体→关系）和图向量混合检索时，提出是否引入 Neo4j 作为图数据库来存储实体关系。

## 决策

**不引入 Neo4j**，继续使用 PostgreSQL + pgvector 作为唯一数据存储方案。

## 理由

1. **检索模式不匹配**：EMA 的核心场景是语义搜索（"我们之前怎么处理 X 问题的？"），不是图遍历——用户不会沿着实体关系图跳转查询。图数据库的优势在这个场景中不是主要检索路径。
2. **pgvector 足够**：向量召回 + 全文检索 + 时间过滤覆盖了 EMA 的实际需求。实体关系可以以 JSON 字段存于 PG 行中，随向量召回的记录一同返回，无需图遍历来发现。
3. **避免过度设计**：目前对图查询的具体需求是推测性的。引入 Neo4j 增加部署复杂度、双写一致性负担，而换不来可验证的用户价值。
4. **约束一致性**：保持 `constraints.md` 中"PostgreSQL + pgvector 作为唯一数据存储方案"的约束不变。

## 不做图数据库的代价

以下代价已认知并接受。每个问题都有具体的缓解措施，且在当前阶段处于可接受范围内。

### 代价 1：递归 CTE 在多跳场景下性能下降

当实体归一化后，跨记忆关系查询需要递归 CTE。随着跳数增加，性能差距逐步拉开：

| 跳数 | 典型数据量 | 递归 CTE 耗时 | Neo4j 耗时 | 对 EMA 的影响 |
|------|-----------|-------------|-----------|-------------|
| 1 跳 | ~100 条边 | < 10ms | < 1ms | ✅ 核心查询模式，完全够用 |
| 2 跳 | ~1,000 条边 | ~50ms | < 5ms | ✅ 偶尔用到，可接受 |
| 3 跳 | ~10,000 条边 | ~500ms-2s | ~20ms | ⚠️ 边界情况，需要时加超时保护 |
| 4+ 跳 | 指数增长 | 几秒到超时 | ~100ms | ❌ 不是 EMA 的查询模式 |

**缓解**：EMA 的核心查询模式是一度关系（"关于 X 我们有什么"），不是多跳图遍历。Phase 1 只做一度关系查询，SQL 直接 JOIN，不需要递归 CTE。当多跳需求真正出现时（见下方"拐点"），再从一度关系查询 API 扩展到递归 CTE。

### 代价 2：多表事务一致性

实体归一化后，数据散在三张表中：

```
写入一条新记忆:
  INSERT INTO memories          ← 记忆本体
  INSERT/UPDATE entities        ← 实体归一化
  INSERT INTO memory_entities   ← 关联表
```

如果第三步失败但记忆本身写入成功，会出现悬空引用——memory 里有实体名但关联表里没有。

**缓解**：用 PostgreSQL 事务包裹三步写入，保证原子性。若写入中途失败（如 LLM 超时），回滚整个事务。极端情况下（事务提交后关联写入失败），Phase 3 的每周巡检会扫描 `memory_entities` 中缺失的关联并补上，最终一致性可接受。

### 代价 3：没有图算法

以下分析能力在 pgvector 上不可用：

| 算法 | 能回答的问题 | 严重程度 | 说明 |
|------|------------|---------|------|
| 度中心性 | "哪个模块是系统的知识枢纽？" | 🟢 低 | 工程团队的查询不是"分析网络结构"，是"找到关于 X 的记忆" |
| 社区发现 | "记忆自然聚成了哪几个主题簇？" | 🟢 低 | 向量搜索 + 实体类型过滤已覆盖分类需求 |
| 最短路径 | "故障 A 和决策 D 之间隔了几层因果链？" | 🟡 中 | 可用递归 CTE 实现，但复杂路径需要手写 Dijkstra。当前无此需求 |

### 代价 4：SQL 可读性衰退

这是长期维护中最真实的问题。同样的查询，Cypher 一行，SQL 十行：

**查"PostgreSQL 的直接关联实体及其关联记忆数量"**：

```sql
-- PostgreSQL（一度关系，已有 entity 表后）
WITH entity_relations AS (
    SELECT me.memory_id, e.canonical_name AS entity_name
    FROM memory_entities me
    JOIN entities e ON e.id = me.entity_id
    WHERE e.canonical_name = 'PostgreSQL'
)
SELECT m.summary, m.source_type, m.created_at
FROM memories m
JOIN entity_relations er ON er.memory_id = m.id
WHERE m.deleted_at IS NULL
ORDER BY m.created_at DESC;
```

```cypher
// Neo4j 版本
MATCH (e:Entity {canonical_name: 'PostgreSQL'})-[]-(m:Memory)
RETURN m.summary, m.source_type, m.created_at
ORDER BY m.created_at DESC
```

**缓解**：一度关系的 SQL 保持在 15 行以内，可读性尚可。当查询 SQL 普遍超过 20 行时（意味着多跳遍历已成为日常需求），就是重新评估的拐点。

## 拐点

当以下条件**同时**满足时，重新评估是否引入图数据库：

1. 团队开始频繁问**"这些记忆之间共同的模式是什么"**，而不是"关于 X 的记忆有哪些"——前者是图分析的领地，后者是向量搜索 + 一度关系
2. 一度关系查询的 SQL 普遍超过 20 行——意味着多跳已成为日常需求
3. 有真实数据支撑决策——而不是凭推测给项目加一个不需要的依赖

到那时，评估将基于实测性能数据和真实查询日志，而非理论推演。

## 后果

- 一度关系查询使用 SQL JOIN，性能足够
- 多跳查询通过 PostgreSQL 递归 CTE 实现，N > 3 跳时性能可能下降，但当前场景不需要
- 没有开箱即用的图算法（中心性、社区发现、最短路径），但当前也不在关键路径上
- SQL 查询的复杂度随关系跳数增长快于 Cypher/图数据库，需在拐点出现时重新评估
- 坚持简单优先原则：先做好单存储，场景验证后再说
