# ADR-005: 不做多租户/多团队隔离

**日期**: 2026-08-04

**状态**: 已接受

## 背景

EMA 基础功能就绪后，在规划进阶扩展时提出：是否需要引入多租户/多团队隔离，让每个团队拥有独立的知识空间。

## 决策

**不做多租户。** 当前按单团队使用设计，不做硬隔离。先引入轻量的 `project` 字段作为命名空间，真正的多租户等到明确的业务信号出现后再评估。

## 理由

### 1. EMA 的核心价值天然反"隔离"

EMA 存在的意义是打破知识孤岛——让架构决策、故障经验、代码知识在团队间流动。同一个公司内，前端团队遇到一个数据库性能问题，恰恰应该能搜到后端团队沉淀的相关记忆。

加了多租户硬隔离，就是在自己产品的核心价值上砌墙。

### 2. 复杂度代价远超当前收益

多租户不是加个 `tenant_id` 列那么简单。它渗透到每一层：

| 层级 | 改动量 |
|------|--------|
| 数据库 | 所有表加 `tenant_id`，所有查询加 `WHERE tenant_id = ?`，向量搜索也得带过滤 |
| API | 认证中间件、JWT/session、租户解析、权限校验 |
| Agent | 每个 tool 调用都得传递 tenant context |
| 前端 | 登录页、团队切换、权限 UI |
| 运维 | 租户管理、配额、数据隔离验证 |

对于一个还在验证核心价值的项目，这些工作会拖慢真正该做的事情。

### 3. 轻量替代方案已足够

在 metadata 层面打 tag 即可满足基本的分组需求：

```python
write_memory(content, metadata={"project": "platform"})
search_memories(query, filters={"project": "platform"})
```

这给了 80% 的隔离效果（默认过滤、允许跨项目搜索），但只有 5% 的复杂度。关键差异：`project` 是可选的——解耦了"我想分组"和"我想建墙"。

## 不做多租户的代价

以下代价已认知并接受。

### 代价 1：上下文污染

当多个团队使用同一个 EMA 实例时，不同团队的记忆会出现在同一个搜索结果中：

```
平台组的记忆:
  "PostgreSQL 连接池默认值 10 不够，生产环境需至少 50"

业务组的记忆:
  "我们的服务只需要 5 个连接，因为 QPS 很低"

EMA 的回答 (问: "连接池配多少合适？"):
  → 两条记忆都检索到了
  → Agent 看到两个矛盾的结论
  → 无法判断哪个适用于你
```

这不是技术问题——EMA 正确地检索到了所有相关知识。问题是**上下文中出现了属于别人场景的答案**。

**缓解**：`project` 字段默认过滤 + 搜索结果标注来源 project，用户能看到"这条记忆来自 platform 组"。

### 代价 2：metadata tag 的维护漂移

`project` tag 靠人维护，人有两个缺陷：

1. **忘了打**——写入时不传 `project`，记忆就全局可见
2. **打不准确**——交叉项目的记忆属于哪个 project？"微服务拆分"可能同时涉及三个团队

一旦 tag 覆盖率掉到 70% 以下，过滤机制就变得不可信——你永远不知道漏掉的那 30% 里有没有其他团队的噪音。

**缓解**：Phase 3 主动巡检扫描缺失 `project` 的记忆，定期提醒补全。但这不是根治方案——根治方案是硬隔离，而硬隔离我们在拐点之前不做。

### 代价 3：缺乏所有权意识

这是最深层的差异：

| | 无隔离 | 有隔离 |
|------|---------|---------|
| 写入心态 | "这个记忆别人也会看到，写模糊一点吧" | "这是我们团队的资产，尽量写清楚" |
| 记忆质量 | 趋于保守、模糊、避免争议 | 趋于具体、可操作 |
| 谁负责养护 | 没人。都是别人的记忆，关我什么事 | "我们的记忆库"，有人管召回、管过期记忆、管矛盾 |
| 采用门槛 | 低——拉个人就能用 | 略高——需要创建空间 |

无隔离时，记忆是**公共厕所**——没人打扫。有隔离时，记忆是**自家的书房**——有人养护。

**缓解**：目前只有一个团队使用，此问题尚未出现。等团队数达到 3+ 时，通过 `project` 字段 + 仪表盘展示各 project 的健康度（覆盖率、召回分布、矛盾数），用可视化激励团队维护"自己的"记忆空间。

## 替代方案：project 命名空间

在需要硬隔离之前，使用 `project` 字段作为轻量命名空间：

```sql
ALTER TABLE memories ADD COLUMN project TEXT DEFAULT 'default';
ALTER TABLE chunks ADD COLUMN project TEXT DEFAULT 'default';
```

| | tenant_id（多租户） | project（命名空间） |
|------|-----|-----|
| 隔离强度 | 硬隔离，跨租户完全不可见 | 软边界，默认过滤，但允许跨项目搜索 |
| 认证要求 | 用户 → 租户绑定，需要登录 | 不需要，请求里带 `?project=platform` 就行 |
| 迁移成本 | 所有 SQL 加 `WHERE tenant_id = ?`，所有 API 加中间件 | 已有的查询加一个可选 filter |
| 跨项目查询 | 不可能（除非做联邦） | `?project=*` 或不传 project 查全部 |

## 用户级认证的迁移路径（多租户前置条件）

用户级认证（知道请求来自谁）与多租户（数据隔离）是正交问题，可独立引入。多租户需在其上绑定"用户 → 租户"，但用户级认证本身不必等拐点：单团队内出现"需要审计谁写了/删了什么"或"需要区分成员与只读者"的信号时，即可先行搭建。三步可独立停在任何一步，每步独立收益，不是"提前过度设计"：

**第 1 步 · key 表**：新建 `api_keys` 表（`id` / `key_hash` 只存 SHA-256、永不存明文 / `owner` / `name` 用途标识 / `created_at` / `revoked_at`），`backend/api/auth.py` 从单 key 常量比较改为查表 + `secrets.compare_digest` 逐行比较。`APP_ENV=test` 豁免与通用 401 语义不变。此步只改认证源头，不动业务读写。

**第 2 步 · 按 key 记 owner**：认证通过后把 `owner` 写入请求级 contextvar（复用 `current_thread_id` / `current_trace_id` 模式），写路径在 `memories.created_by` / `deleted_by`、`llm_usage.owner` 落 owner。审计到位：usage trace 可回答"哪个 key 花了多少钱、调了什么"，记忆变更可回答"谁删的"。

**第 3 步 · 按 owner 过滤**：读路径按 `created_by = :owner` 过滤或分权限档（读全部 / 只读自己的 / 只写自己的），前端加登录/换 key 流程，`VITE_EMA_API_KEY` 构建注入退役——bundle 不再含共享 key。

**与现有机制的关系**：`ratelimit.py` 已按 Bearer token 分桶，换 per-user key 后天然成为 per-user 限流，无需改造；`project` 命名空间（上文）管"分不分组"，`owner` 管"谁干的、谁能动"，两维正交。

**当前保持共享 key 不是缺陷**：单团队、无审计需求、无只读成员时维持现状（威胁模型见 `docs/architecture.md`「API Security」）。

## 拐点

当以下三个信号**同时**出现时，引入真正的多租户：

1. **超过 5 个团队共用一个实例**
2. **有团队明确提出"有些记忆不想让其他团队看到"**（安全需求，不是组织需求）
3. **有人愿意为隔离能力付费**（SaaS 信号）

到那时，评估将基于真实的查询模式、数据量、团队使用习惯，知道隔离的粒度应该是什么（按团队？按 project？按 repo？），而不是现在靠猜来设计。

## 后果

- 当前按单团队使用设计，接入认证为共享 API key（`EMA_API_KEY`，所有 `/api` 请求须携带 `Authorization: Bearer <key>`，见 `backend/api/auth.py`），无用户级认证系统（登录 / 会话 / 用户身份 / 角色权限），无租户隔离
- 通过 `project` 字段提供轻量命名空间，默认不过滤，用户可按需过滤
- 上下文污染和 tag 漂移是可接受的已知风险
- 没有团队所有权意识可能影响记忆质量——通过仪表盘和巡检激励养护
- 等待拐点出现时，用"先单团队，预留扩展"的策略而非提前过度设计
