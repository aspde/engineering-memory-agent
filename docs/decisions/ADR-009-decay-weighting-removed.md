# ADR-009: 记忆排序移除衰减加权（decay_factor）

**日期**: 2026-08-11

**状态**: 已接受

## 背景

记忆检索排序最初在相似度上乘一个艾宾浩斯遗忘衰减因子（`similarity × decay_factor`），目标是"常用知识浮上来、过时知识沉下去"。衰减因子由召回历史按 `S=1+(recall+1)·2` 计算，半衰期 ≈ 0.69·S 小时——从未被召回的记忆约 2 小时减半，cold band 整体衰减到 ≈0。

该机制有两个问题，其中一个直到做了 A/B 才暴露：

1. **前提未经验证**：「近期/高频 = 相关」建立在合成老化分布上，没有真实语料支撑。
2. **测量显示它让检索变差**（见 `tests/eval/reports/decay_ab_report.md`）。

## 决策

**从记忆排序路径移除衰减加权**：

- `search_memories` 改为单段 HNSW 按纯相似度排序（`ORDER BY embedding <=> :vec`），不再有两段候选窗 + Python 重排。
- 召回历史保留为**元数据**：`record_recalls` 单条 `UPDATE ... WHERE id = ANY(:ids)` 批量递增 `recall_count`/`recalled_at`，不参与排序。
- "记忆是否过期"改由人/LLM 基于原始访问历史判断：`search_memories_tool` 展示行带 `recalls` 与 `last_recalled`，patrol 的过期记忆扫描让 LLM 直接读这两个字段，不再依赖机器算出的衰减因子。

## 理由

1. **唯一的测量数据表明衰减让检索变差**：decay A/B 在合成老化分布上跑同一 30 条 query 双臂，decay on recall@5 **0.667**、decay off **0.900**（MRR 0.622 vs 0.825、NDCG 0.633 vs 0.844，约 10 条 query 的目标记忆被压出 top-5）。
2. **调参轨迹本质是"把该删的功能调成无害"**：S 乘数从 2 → 8 → 12、加 0.10 保留 floor 后，recall@5 从 0.367 → 0.633 → 0.667 单调逼近无衰减的 0.900——每轮调参都只是缩小损伤，无法消除。继续调参是维护一个测量证明有害的功能。
3. **前提无真实语料支撑**：「近期/高频 = 相关」只在合成分布上成立，真实记忆库里冷门但关键的旧决策被埋掉的代价没有真实数据可辩护。
4. **替代方案成本低**：`record_recalls` 本来就在记访问历史，把它从"排序输入"降级为"元数据"，语义反而更诚实——`recall_count` 记的是"被任意查询返回过"，不是"被用过"，本就不该改变排名。

## 代价与保留

- **`decay_factor` 列冻结为历史遗留**：原决策保留列以免迁移历史行。当前生产库为空（仅 70 条评估种子），该列无任何代码维护，仅一句 docstring 引用——空库上删列无迁移成本，是否删除作为独立事项评估，不并入本次决策。
- **召回统计语义变化**：`recall_count`/`recalled_at` 定位为访问历史元数据（UI 展示、patrol 归档判断的输入），不是排序信号，垃圾查询"强化记忆"的危害消失（它不改变排名）。
- **"过期"判断从公式移交给人/LLM**：判据更主观但更符合工程实际——过时与否由使用方读原始访问历史决定，而不是由机器公式决定。

## 拐点

当以下任一条件出现时，重新评估是否把召回历史重新引入排序：

1. 出现真实语料证据表明「近期/高频 = 相关」成立（真实衰减分布统计，而非合成分布）。
2. 排序信号确实需要区分冷热记忆，且 A/B 显示引入衰减不降 recall（当前数据方向相反）。

## 后果

- `search_memories` 单段 HNSW 纯相似度，代码路径简化（删掉两段候选窗 + Python 重排）。
- `record_recalls` 保留，作为 patrol 归档与 UI 展示的输入。
- `docs/memory-system.md` §4 与 `docs/engineering/gap-remediation.md` §6.1 的衰减论证现由本文档统一记录，决策可追溯。
- 完整测量数据见 `tests/eval/reports/decay_ab_report.md`；口头记录见 `docs/engineering/decision-faq.md` 第 7 节。
