# EMA 技术决策问答

> 项目演进过程中被反复追问的技术决策及其依据，按主题整理。每条都对应真实代码，可追溯验证。完整证据与审查记录见 [code-review-findings.md](./code-review-findings.md)。

## 一、检索与评估

### 1. 四级相似度阈值 0.85/0.72/0.60 是怎么定的？

阈值不是拍脑袋，是标定出来的（`tests/eval/experiments/threshold_calibration.py`）：收集三类摘要对的 BGE-M3 相似度分布——同一知识的 LLM 同义改写（应 merge）、同类不同记忆（不该 merge）、异类（应 new）。结果：同义改写对相似度 0.84-0.97（p25 0.878），同类不同记忆上限只有 0.79——**旧值 0.92 高到一半该 merge 的同义对被漏成冲突检测**。0.85 是自然分离点（高于同类上限、低于同义下界），把 MERGE 0.92→0.85、CONFLICT 0.75→0.72（跟随下移）。改后同一知识被不同来源写入时能正确合并。边界：8 对改写样本小，真实生产的重复摘要分布待部署后确认。

### 2. 检索是读操作，为什么每次检索都写 recall_count？

每次命中记忆记录一次召回（`record_recalls` 单条 `UPDATE ... WHERE id = ANY(:ids)` 批量递增 `recall_count`/`recalled_at`），替代了原 `update_decay_batch` 的 N+1 写法和并发丢计数问题。诚实边界：`recall_count` 记的是"被任意查询返回过"，不是"被用过"——它定位为访问历史元数据（UI 展示、patrol 归档判断的输入），不是排序信号，所以垃圾查询"强化记忆"的危害不存在了（它不改变排名）。

### 3. multi-query 并集截断、sparse 先截断再过滤，这些是全局最优吗？

不是——multi-query 并集按插入序截断、sparse 候选先按 id 截断再算 Jaccard，这些都是确定性偏差的边界近似。在万级以下语料影响可忽略（记忆路径的向量检索是单段 HNSW 直接按相似度排序，无两段窗口）。

### 4. 评估数字 1.0 是自证吗？数字可信吗？

早期 Recall@5=1.0 是 30 条种子语料上的自评结果，query 从种子记忆手工标注、每条只标一条相关记忆，含金量有限——定位为回归基线而不是能力上限，并把评估集扩充到 70 条（5 类 × 14、hard 占 30%，语料和 query 都翻倍）。生产 memory 路径**默认确定性基线**现在 0.886/0.767（纯子串匹配，70 条语料上 8 条 miss）；语义通道是显式 opt-in（用被评测模型自评所以非默认）。真实判别力看 27 条 hard-negative：纯向量综合通过仅 59.3%，已用 bounded cross-encoder top-3 重排提到 81.5%。`task completed=0.5` 和 `unexpected_rate=0.375`（DeepSeek 过度调工具）比任何完美数字更能说明 Agent 的生产行为。

### 5. LLM judge 可信吗？

judge 用独立 provider 是强制的（避免被测模型给自己打分），但 judge 本身有个已知误判（ans-006 把允许改写当耳边风判 grounded=false），记为 known_anomaly。LLM-judge 的 groundedness 是参考值不是绝对值——deterministic judge 才是门禁。

### 6. 单次跑的数字能代表能力吗？

不能。LLM 行为方差大是真实挑战，测过同一天跑两次 relation_recall 从 0.53 掉到 0.34。所以门禁不能用单次采样当能力——用多次均值 ± 置信区间判红（`tests/eval/multi_run_gate.py`，N 次运行均值 + 95% CI 下限，CI 改 3 次均值）。

### 7. 衰减加权为什么被移除？

衰减系统最初是"让常用知识浮上来、过时的沉下去"的卖点，但 decay A/B（合成老化分布上跑双臂）给出唯一测量：衰减加权 recall@5 0.667、纯相似度 0.900。更关键的是调参轨迹——S 乘数从 2 调到 8 再到 12、加 0.10 floor，recall 从 0.367 → 0.633 → 0.667 单调逼近无衰减的 0.900：这是在把一个该删的功能调成无害。且其前提「近期/高频=相关」只建立在合成分布上。所以移出排序路径：`search_memories` 纯相似度单段 HNSW，`record_recalls` 保留访问历史作元数据，过期归档交给 patrol LLM 读原始 `recalls`/`last_recalled` 判断。教训：能用测量否掉自己的功能，比维护测量证明有害的功能更有价值。决策记录见 [ADR-009](../decisions/ADR-009-decay-weighting-removed.md)。

### 8. 对话延迟和成本是多少？

`measure_chat_p95.py` 跑了 10 轮真实对话（真实 DeepSeek + 本地 BGE-M3 + 完整检索路径），端到端 P95 73.6s、平均 35.9s。主要耗时在 LLM 重排：每轮对话约 19 次 `rerank_llm`、约 40s，这是模型被工具 schema 允许自主把 `use_llm_rerank=True` 传给检索工具导致的。已做三件事：① 从三个检索工具的 schema 移除 `use_llm_rerank` 参数；② 用 task_eval 验证移除后任务完成率 0.500 持平、答案 groundedness 1.000 不变；③ P95 预期降到大半。成本上 10 轮合计 285.9k tokens、估算 $0.081（约 ¥0.06/轮）。决策记录见 [ADR-010](../decisions/ADR-010-llm-rerank-locked-from-tools.md)。

### 9. 记忆召回统计和 LLM rerank vs CE 的结果是什么？

**LLM rerank vs bounded cross-encoder** 在生产 memory 路径上：recall@5 完全一样（0.900）——rerank 不改变召回集合；MRR 从 0.819 微升到 0.833（+0.014），但平均延迟从 2.5s 涨到 14.1s（5.5x，每候选一次 LLM 调用）。结论：小语料下 rerank 只微调排序、不救召回，收益 scale-dependent——和 hybrid 路径 cross-encoder 有害（0.967 vs 1.000）的结论一致。

**衰减 A/B 的结局**：原公式 `S=1+2·recall` 半衰期太短，合成老化分布下 recall@5 从 0.900 掉到 0.367（19/30 目标被压出 top-5）。调参到 `S=12 + floor 0.1` 后 recall 回升到 0.667、MRR 0.622——但始终低于无衰减的 0.900。这个"调成无害"的信号加上无真实语料支撑的前提，最终促成衰减从排序路径移除（见第 7 节）。

## 二、安全与认证

### 10. 前端 bundle 里有 key，认证防谁？

单 key 是 ADR-005 无多租户的推论，key 打进前端 bundle 等于公开，而且全站没有任何 API 限流，成本没有上限。生产上做三层：网关按 IP+key 做令牌桶限流、服务端签发短期凭证（前端不再持有静态 key）、把 `/api/memory/ingest` 这类重写入路径单独限流。

### 11. 为什么测试环境绕过认证用环境变量，而不是依赖注入？

这是可审计的隐患——测试安全和生产安全共用一个进程级环境变量开关。正确做法是测试用 FastAPI 的 `dependencies_overrides` 或 fixture 注入替代认证。这是设计问题，不是 feature。

### 12. webhook 没配 secret 怎么处理？

production 是 fail-closed——没配 secret 直接拒绝，这层是对的。但两个默认值（development + 无 secret）叠加等于裸奔，所以生产部署时 secret 是强制的，不是可选项。

### 13. 为什么有两套连接池、迁移流程是什么？

双池是驱动差异（asyncpg 和 psycopg 各自需要）的技术债，不是设计——它们互不感知、参数写死。更值得担心的是"每次启动清向量列换维度"：误配 `EMBEDDING_MODEL` 会清空生产向量。已引入 Alembic 迁移（`alembic_version` 表 + upgrade/downgrade 成对迁移，基线固化 9 表，新库/旧库/回滚三路径已实测），让 schema 演进可回滚。**后续（2026-08-11）**：`init_db` 已改为只校验不自动清空——维度不匹配直接启动失败 + `python -m scripts.recreate_db` 重建，"误配清空向量"风险已消除。

## 三、实体与写入

### 14. 实体归一化可靠吗？进程重启未完成的归一化会怎样？

fire-and-forget 不阻塞写入是有意取舍；但进程重启未完成的归一化就丢了（只能手动重跑脚本），merge 掉实体后 `memory_entities` 里的旧链接永不清除，0.85 阈值也没有准确率测量——这两个是真缺口。方案是周巡检补偿 + 定期 cleanup 脚本。

### 15. chat_sync 用在哪？

生产没有任何调用方，是为接口对称性加的，真实使用者只有测试。这是过度设计，实际应该删掉，让每个 provider 只维护一套客户端。

### 16. 记忆库会不会被写坏？写入侧有什么防线？

记忆写入是系统里唯一"不可逆 + 一次写坏会无限复用"的操作——读错了下次还能再读，写错了它变成检索候选、影响之后所有回答。所以读侧用指标防（Recall/MRR），写侧用设计防，完整防线分六层（完整表含代码位置见 [deep-dive.md](./deep-dive.md) 的「写入侧质量防线」，此处只列防线与失败语义）：

| 层 | 防线 | 失败语义 |
|----|------|---------|
| 1 精确去重 | content-hash 幂等门：精确重复在 LLM 抽取前停住；`meta.prior_hashes` 保留被合并/覆盖的旧 hash，重放与重摄取永远命中 | 零 LLM 成本，防重放污染 |
| 2 抽取降级 | 摘要 LLM 挂 → 原文前 200 字回退；实体/关系重试耗尽 → 降级 `[]` + ERROR + `ema_structured_failures_total`；关系端点必须落在已提取实体集合内（防幻觉端点） | 增强类失败降级，内容不丢 |
| 3 阈值分级 | 四级相似度去重，阈值经标定：0.85 合并 / 0.72 冲突 / 0.60 关联 / <0.60 新增 | 边界带本身有噪声，所以"冲突"的后果不落在默认路径上 |
| 4 矛盾不静默 | agent 路径 `interrupt()` 等人；webhook/连接器入 `pending_conflicts` 队列；检测失败降级 supplement；每周巡检全量矛盾扫描兜底旧矛盾（巡检默认关闭，`PATROL_ENABLED=true` 开启，见 [ADR-011](../decisions/ADR-011-breadth-default-off.md)） | 单点漏判不会变成永久的自相矛盾 |
| 5 HITL 审批 | 写/摄取工具执行前等人确认；巡检无人值守，冲突自动 keep_both（上限 3 次） | 产品层最后防线 |
| 6 可逆 | 所有删除是 `deleted_at` 软删；patrol 冲突可 reopen；裁决留台账 | 判错可重裁，无不可逆破坏点 |

两个最容易答错的失败语义（旧文档都写错过，以代码为准）：**增强类（实体/关系）失败大声降级 + 失败计数**；**矛盾检测失败保守降级为 supplement 关联写入**——不假定矛盾（那会丢弃内容或把非矛盾误路由到 HITL），也不把新内容无标记写进冲突记忆，漏网由每周巡检兜底。不是"假定无冲突"，也不是"传播失败不落库"。

三条诚实边界（主动交代，比防线本身更可信）：
1. **merge 忠实度是唯一静默风险点，且没测**（见下条）
2. **矛盾检测只 vet 最近匹配**——第 2/3 近邻只记 supplement、不逐一 vet（每个近邻多一次结构化 LLM 调用，为罕见事件买单，权衡后拒绝），近邻矛盾靠周巡检兜底
3. **`_has_substance` 守卫只在 auto-memory 路径生效**——它拒绝"摘要退化成原文截断 + 零实体"的 LLM 故障产物，但 webhook/连接器摄取不走该守卫

### 17. merge 会把记忆合并坏吗？合并忠实度测过吗？

诚实说：**没测过**，这是记忆系统写入侧最该补的评估。两条摘要合一条，若 LLM 丢了旧记忆的事实、或写了旧记忆没有的内容，判断（该不该合，阈值分级）与操作（合成，LLM）都是 LLM、无外部校验——这是当前唯一的静默风险点。

设计层的缓解（不依赖测量）：合并失败保留原摘要（合并是自由文本，失败成本是"少合并一次"）；内容哈希幂等 + `prior_hashes` 保证任何合并/覆盖可重放；实体/关系合并是确定性去重（`_merge_entities` 按 name、`_merge_relations` 按 (from,to,type)），不受 LLM 影响。

要补的测量：20-30 对已知摘要对，让 judge provider（独立于被测模型的裁判通道）打分"合并后摘要是否覆盖了两条旧摘要的全部事实"，跑出丢事实率。优先级高于新增连接器/场景——记忆系统最该测的是"写没写坏"，不是"查得快不快"。

## 四、架构与工程实践

### 18. 为什么不用 LangChain Agent？

黑盒 + HITL 控制弱 + 调试代价。如果公司已有 LangChain 基础设施——框架只是薄封装，核心价值在记忆/检索/韧性层，迁移不改这些。LangGraph 的价值在 interrupt/checkpoint/流式，超出这三点就回归普通编排。

### 19. 数据量这么小有意义吗？

这个量级足够支撑技术决策——万级记忆库 pgvector HNSW 完全够用，性能瓶颈远未到来，这是拐点思维。但诚实地说，生产级规模没跑过，这是评估的上限。

### 20. 没有团队怎么保证质量？

这个项目是一个人的团队，所以用团队工程的纪律约束自己：ADR 记录每个选型为什么、CI 把关每个提交、评估集量化每次检索改动。承认这替代不了真实的 code review——review 能发现的跨模块问题和视角盲区，是这个项目最大的风险敞口。

### 21. 重做的角度：哪些是取舍、哪些是疏漏

**有意决策**（ADR 撑腰）：不做多租户 / 不用 Neo4j / 单 Agent / 不做场景自动路由 / 无用户级认证（有 API key 接入认证）。**已知疏漏**（老实认）：无真实用户流量（对话 P95 73.6s / ≈¥0.06 每轮为实测，非生产流量）。
