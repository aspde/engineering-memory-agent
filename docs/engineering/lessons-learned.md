# EMA 项目演进与决策复盘

> EMA 演进过程中的关键技术决策复盘。每个决策记录了当时的情境、权衡、采取的行动和最终结果——哪些决策被验证正确，哪些差点做错，哪些是真实的疏漏。

---

## 复盘 1：Agent 框架选型——LangGraph 而非 LangChain Agent

**情境**：项目启动时要选 Agent 框架。主流推荐是 LangChain 的 create_react_agent，上手快、文档多、社区活跃。

**权衡**：在"快速上手"和"长期可控"之间取舍。决策影响后续所有功能的实现方式，改框架成本极高。

**行动**：
1. **先做原型对比**：用 LangChain Agent 和 LangGraph StateGraph 各搭一个最小 ReAct 循环，模拟核心场景——LLM 调 tool + 中途暂停等审批
2. **发现关键差异**：LangChain Agent 的 HITL 是回调式，暂停后恢复的路径不好控制；LangGraph 的 `interrupt()` + `Command(goto=...)` 是图原语，能精确指定"暂停后去哪个节点"
3. **写 ADR 记录决策**：把"为什么选 LangGraph、为什么不用 LangChain Agent、未来什么场景会重新评估"写成 [ADR-001](../decisions/ADR-001-langgraph.md)
4. **验证**：用原型对比的代码 demo 验证——LangChain Agent 插入"写操作前审批"卡点需要 hack 内部流程，LangGraph 是声明式的

**结果**：
- 选了 LangGraph，后续实现 HITL 审批和冲突仲裁两个卡点时，确实像预期那样声明式插入，没有 hack
- 决策记录在 [ADR-001](../decisions/ADR-001-langgraph.md)，至今没改过
- 形成习惯：**所有技术选型都写 ADR**，记录"为什么做、为什么不、拐点是什么"

**后续验证**：LangChain 后来废弃了 create_react_agent，说明方向正确。框架只是薄封装，核心价值在记忆/检索/韧性层——如果公司已有 LangChain 基础设施，迁移不改这些，LangGraph 的价值在 interrupt/checkpoint/流式，超出这三点就回归普通编排。

## 复盘 2：记忆去重与冲突检测——阈值用数据标定，不拍脑袋

**情境**：记忆库快速膨胀。同一个知识点从 Git、飞书、PingCode 多个来源反复写入，导致：1) 记忆重复严重；2) 矛盾信息被同时存下来。

**权衡**：去重机制必须满足——不能粗暴去重丢信息；矛盾信息不能自动合并；不能每次写入都调 LLM（成本太高）。

**行动**：
1. **分层筛选**：先用向量相似度做粗筛（便宜），90% 的写入用一次向量搜索解决
2. **设计四级阈值**：≥0.85 合并 / 0.72-0.85 冲突检测 / 0.60-0.72 补充关联 / <0.60 全新插入
3. **阈值标定**：收集三类摘要对（同义改写 / 同类不同记忆 / 异类）算相似度分布，发现旧值 0.92 高到同义改写对一半漏 merge，0.85 是自然分离点（`tests/eval/threshold_calibration.py`）
4. **容错降级**：LLM 合并失败保留原摘要，冲突检测失败假定无冲突——保证写入总能成功
5. **冲突走 HITL**：矛盾时不自动处理，`interrupt()` 暂停让用户在 4 个选项里选

**结果**：
- 记忆库膨胀问题解决，90% 写入只调一次向量搜索，LLM 调用成本可控
- 矛盾信息不再被自动合并，由用户仲裁，避免知识污染
- 这个设计成了 EMA 的核心差异化能力，写进了 [memory-system.md](../memory-system.md)

**边界**：阈值标定样本小（8 对改写），真实生产的重复摘要分布待部署后确认。

## 复盘 3：差点引入 Neo4j——技术选型由查询模式驱动，不是由数据结构名驱动

**情境**：Phase 1 做实体图谱时，一开始想用 Neo4j 存实体关系。当时觉得"图谱就该用图数据库"，选型很顺理成章。

**行动**：
1. **差点引入 Neo4j**：写了技术方案，准备加 Neo4j 依赖
2. **被自己问倒**：写 ADR 时列"为什么用 Neo4j"，发现答不上来——EMA 的核心查询是"关于 PostgreSQL 我们有什么记忆"（一度关系），不是多跳图遍历。Neo4j 的优势用不上
3. **算代价**：Neo4j 要和 PG 双写，一致性负担大；部署多一个组件；运维复杂度上升
4. **改方案**：用 PG 表存实体，一度关系用 SQL JOIN，15 行以内可读。写了 [ADR-005](../decisions/ADR-005-no-neo4j.md)
5. **定拐点**：当 SQL 普遍超过 20 行、团队频繁问"记忆的共同模式"时再评估

**结果**：
- 省了一个组件的运维成本，一度关系查询性能完全够（< 10ms）
- 这次"差点过度设计"形成了习惯：**所有新依赖先问"它解决什么问题、不用会怎样、拐点是什么"**
- 后来 Phase 1 实施验证了决策正确——多跳需求根本没出现

**反思**：差点陷入"技术选型追时髦"的陷阱。"图谱就该用图数据库"是个看起来合理的偏见，但实际查询模式不匹配。技术选型要由查询模式驱动，不是由数据结构名字驱动。拐点未出现就一直不用 Neo4j，如果出现多跳需求，先用递归 CTE 顶，顶不住再考虑。

## 复盘 4：不做"场景间自动路由"——反对需求时先挖真实诉求

**情境**：Phase 4 做垂直场景时，使用者提出要做"场景间自动路由"——用户说一句话，EMA 自动判断该走故障复盘还是代码审查场景。觉得不该做。

**行动**：
1. **先理解真实诉求**：问为什么想要自动路由。对方说的其实是"用户不想手动选场景，太麻烦"
2. **拆解问题**："用户嫌麻烦"和"自动路由"是两件事。前者是 UX 问题，后者是架构问题
3. **提替代方案**：建议在聊天页侧边栏加场景快捷入口（按钮组），用户一键进入场景。自动路由留到场景数 >10 再考虑
4. **用 spec 锁定**：在 [Phase 4 spec](../design/phase-4-vertical-scenarios-spec.md) 的 Out of Scope 里明确写"不做场景间自动路由"并写明理由
5. **数据说话**：先用快捷入口版跑两周，看用户反馈。结果没人抱怨要自动路由

**结果**：
- 没做自动路由，省了至少 1 周开发（意图分类器、场景路由逻辑、冲突处理）
- 快捷入口方案用户接受度很好
- 教训：**反对需求时要先挖真实诉求，往往有更轻的解法**

**判断原则**：是否违反架构原则决定坚持还是妥协。自动路由违反"简单优先"（场景数才 4 个），所以坚持；UI 细节则妥协。

## 复盘 5：从 0 到 1 的推进方式——验证 → 最小原型 → 路线图 → 小步快跑

**情境**：项目源于一个想法——团队知识流失严重，新人 onboarding 慢。没人安排做这个。

**行动**：
1. **先做问题验证**：找 3 个入职半年的新人聊，问 onboarding 最痛的点。发现核心不是"没有文档"，是"不知道为什么这么设计"，答案都在老人脑子里和飞书历史里
2. **做最小原型**：搭了"Git commit → LLM 提取 → pgvector 检索"的最小链路，跑通"问 EMA 一个问题，从 Git 历史里找答案"
3. **写 ADR 路线图**：原型验证后写 [ADR-006](../decisions/ADR-006-extension-roadmap.md) 四阶段路线图，不盲目扩展
4. **小步快跑**：每个 Phase 1-2 周交付，交付后给团队试用收集反馈，再决定下一个 Phase 做什么
5. **坚持简单优先**：每个 Phase 只做"解锁下一步的最小能力"，不做过度设计（不做多租户、不做 Neo4j）

**结果**：
- 4 个 Phase 全部闭环，从想法到可用产品
- 这个项目成为验证"端到端主导 + 工程纪律替代 review"的完整样例：ADR 记录决策、CI 把关提交、评估集量化改动、1450+ 测试兜底

**坦诚的边界**：项目确实没有团队兜底，这是最坦诚的短板。团队 review 能抓到流程抓不到的东西——比如"score 阈值触发改写"的假设是被评估数据打脸的，而不是被 review 打脸的。这也是缺的视角：不是做系统的能力，是被 review 的视角。
