## 案例 1：技术选型决策（最常被问）

**问题**：讲一个你做过的有争议的技术选型决策。

### S (Situation)
EMA 项目启动时，要选 Agent 框架。团队里有人推荐用 LangChain 的 create_react_agent，因为上手快、文档多、社区活跃。我当时是 [需要你补充：角色，如项目主程]，要为整个技术栈负责。

### T (Task)
我需要在"快速上手"和"长期可控"之间做权衡。决策影响后续所有功能的实现方式，改框架成本极高。

### A (Action)
1. **先做原型对比**：用 LangChain Agent 和 LangGraph StateGraph 各搭了一个最小 ReAct 循环，模拟 EMA 的核心场景——LLM 调 tool + 中途暂停等审批
2. **发现关键差异**：LangChain Agent 的 HITL 是回调式，暂停后恢复的路径不好控制；LangGraph 的 `interrupt()` + `Command(goto=...)` 是图原语，能精确指定"暂停后去哪个节点"
3. **写 ADR 记录决策**：我把"为什么选 LangGraph、为什么不用 LangChain Agent、未来什么场景会重新评估"写成 ADR-001，留档可追溯
4. **说服反对意见**：我把原型对比的代码 demo 给团队看——LangChain Agent 要插入"写操作前审批"卡点需要 hack 内部流程，LangGraph 是声明式的。最终大家认可

### R (Result)
- 选了 LangGraph，后续实现 HITL 审批和冲突仲裁两个卡点时，确实像预期的那样声明式插入，没有 hack
- 决策记录在 [ADR-001](file:///g:/Projects/ema/docs/decisions/ADR-001-langgraph.md)，到现在没改过
- 这次经历让我形成习惯：**所有技术选型都写 ADR**，记录"为什么做、为什么不、拐点是什么"

**追问预案**：
- Q：LangChain Agent 真的那么差吗？→ A：不是差，是抽象层级不同。它是"开箱即用"，适合简单场景。EMA 需要 HITL 精确控制，它的抽象反而成了阻碍
- Q：如果现在重新选会变吗？→ A：不会。后来 LangChain 自己也废弃了 create_react_agent，说明方向是对的

## 案例 2：攻克技术难题

**问题**：讲一个你遇到的最难的技术问题，怎么解决的。

### S (Situation)
EMA 上线初期，记忆库快速膨胀。同一个知识点从 Git、飞书、PingCode 多个来源反复写入，导致：1) 记忆重复严重；2) 有时矛盾的信息被同时存下来（比如"连接池配 10"和"连接池配 50"）。

### T (Task)
我要设计一套去重和冲突检测机制，要求：1) 不能粗暴去重丢信息；2) 矛盾信息不能自动合并；3) 不能每次写入都调 LLM（成本太高）。

### A (Action)
1. **分层筛选**：先用向量相似度做粗筛（便宜），把 90% 的写入用一次向量搜索解决
2. **设计四级阈值**：
   - ≥0.92：几乎是同一条 → LLM 合并摘要
   - 0.75-0.92：可能相关 → LLM 检测矛盾 → 矛盾走 HITL 仲裁，不矛盾补充关联
   - 0.60-0.75：弱相关 → 插入新记忆但建立关联
   - <0.60：全新 → 直接插入
3. **阈值调参**：0.92/0.75/0.60 不是拍脑袋，是拿真实数据测出来的——0.92 是"几乎是同一条"的边界，0.75 是"可能相关"的边界
4. **容错降级**：LLM 合并失败保留原摘要，冲突检测失败假定无冲突——保证写入总能成功
5. **冲突走 HITL**：矛盾时不自动处理，`interrupt()` 暂停让用户在 4 个选项里选（keep_existing/overwrite/merge/keep_both）

### R (Result)
- 记忆库膨胀问题解决，重复率从 [需要你补充：如 40%] 降到 [需要你补充：如 5%]
- 矛盾信息不再被自动合并，由用户仲裁，避免知识污染
- 90% 写入只调一次向量搜索，LLM 调用成本可控
- 这个设计成了 EMA 的核心差异化能力，写进了 [memory-system.md](file:///g:/Projects/ema/docs/memory-system.md)

**追问预案**：
- Q：阈值怎么测的？→ A：拿了一批已知是否重复的记忆对，算它们的向量相似度，看分布。0.92 以上基本都是同一条，0.75-0.92 是相关但不同，0.6-0.75 是沾边
- Q：LLM 冲突检测准确率？→ A：没系统测过，但 prompt 强制 JSON 输出 + fails safe（失败假定无冲突），错了由用户在 HITL 兜底

## 案例 3：失败与复盘

**问题**：讲一个你做失败的事情。

### S (Situation)
EMA Phase 1 我做实体图谱时，一开始想用 Neo4j 存实体关系。当时觉得"图谱就该用图数据库"，技术选型很顺理成章。

### T (Task)
做技术方案设计时，我需要决定实体和关系存哪里。

### A (Action)
1. **差点引入 Neo4j**：写了技术方案，准备加 Neo4j 依赖
2. **被自己问倒**：写 ADR 时我列了"为什么用 Neo4j"，发现答不上来——EMA 的核心查询是"关于 PostgreSQL 我们有什么记忆"（一度关系），不是多跳图遍历。Neo4j 的优势用不上
3. **算代价**：Neo4j 要和 PG 双写，一致性负担大；部署多一个组件；运维复杂度上升
4. **改方案**：用 PG 表存实体，一度关系用 SQL JOIN，15 行以内可读。写了 [ADR-005](file:///g:/Projects/ema/docs/decisions/ADR-005-no-neo4j.md) 记录"为什么不用、什么时候重新评估"
5. **定拐点**：当 SQL 普遍超过 20 行、团队频繁问"记忆的共同模式"时再评估

### R (Result)
- 省了一个组件的运维成本，一度关系查询性能完全够（< 10ms）
- 这次"差点过度设计"让我形成习惯：**所有新依赖先问"它解决什么问题、不用会怎样、拐点是什么"**
- 后来 Phase 1 实施验证了决策正确——多跳需求根本没出现

**反思**：差点陷入"技术选型追时髦"的陷阱。图谱就该用图数据库——这是个看起来合理的偏见，但实际查询模式不匹配。**技术选型要由查询模式驱动，不是由数据结构名字驱动**。

**追问预案**：
- Q：怎么发现差点过度设计的？→ A：写 ADR 时被自己问倒。ADR 强制写"为什么"，写不出来就是信号
- Q：现在还是不用 Neo4j 吗？→ A：是。拐点没出现。如果出现多跳需求，会先用递归 CTE 顶，顶不住再考虑

## 案例 4：团队协作 / 需求冲突

**问题**：讲一个你和需求方意见不一致的情况。

### S (Situation)
EMA Phase 4 做垂直场景时，[需要你补充：如团队成员 / 使用者] 提出要做"场景间自动路由"——用户说一句话，EMA 自动判断该走故障复盘还是代码审查场景。我觉得不该做。

### T (Task)
我要么硬扛拒绝，要么妥协做。需要找到既不破坏架构原则又能解决对方真实诉求的方案。

### A (Action)
1. **先理解真实诉求**：我问他为什么想要自动路由。他说的其实是"用户不想手动选场景，太麻烦"
2. **拆解问题**：我发现"用户嫌麻烦"和"自动路由"是两件事。前者是 UX 问题，后者是架构问题
3. **提替代方案**：我建议在聊天页侧边栏加场景快捷入口（按钮组），用户一键进入场景，不用打字描述。自动路由留到场景数 >10 再考虑
4. **用 spec 锁定**：在 [Phase 4 spec](file:///g:/Projects/ema/docs/design/phase-4-vertical-scenarios-spec.md) 的 Out of Scope 里明确写"不做场景间自动路由"，并写明理由
5. **数据说话**：我让他先用快捷入口版跑两周，看用户反馈。结果没人抱怨要自动路由

### R (Result)
- 没做自动路由，省了至少 1 周开发（要加意图分类器、场景路由逻辑、冲突处理）
- 快捷入口方案用户接受度很好
- 这次让我学到：**反对需求时要先挖真实诉求，往往有更轻的解法**

**追问预案**：
- Q：万一他坚持要自动路由呢？→ A：我会让他先做 MVP 验证——用最简陋的意图分类跑一周，看准确率。数据说话比争论有效
- Q：你怎么判断该坚持还是妥协？→ A：看是否违反架构原则。自动路由违反"简单优先"（场景数才 4 个），所以我坚持。如果是 UI 细节我会妥协

## 案例 5：主动推进 / 从 0 到 1

**问题**：讲一个你主动承担、超出职责的事情。

### S (Situation)
EMA 一开始只是我的一个想法——团队知识流失严重，新人 onboarding 慢。但没人安排我做这个，[需要你补充：如本职工作是 XXX]。

### T (Task)
我要在完成本职工作之余，把这个想法验证成可用的东西。

### A (Action)
1. **先做问题验证**：我找了 3 个入职半年的新人聊，问他们 onboarding 最痛的点。发现核心不是"没有文档"，是"不知道为什么这么设计"，答案都在老人脑子里和飞书历史里
2. **做最小原型**：用周末时间搭了"Git commit → LLM 提取 → pgvector 检索"的最小链路，跑通了"问 EMA 一个问题，从 Git 历史里找答案"
3. **写 ADR 路线图**：原型验证后，我写了 [ADR-006](file:///g:/Projects/ema/docs/decisions/ADR-006-extension-roadmap.md) 四阶段路线图，让自己不盲目扩展
4. **小步快跑**：每个 Phase 1-2 周交付，交付后给团队试用收集反馈，再决定下一个 Phase 做什么
5. **坚持简单优先**：每个 Phase 只做"解锁下一步的最小能力"，不做过度设计（比如不做多租户、不做 Neo4j）

### R (Result)
- 4 个 Phase 全部闭环，从想法到可用产品 [需要你补充：如 3 个月]
- [需要你补充：如 团队 X 人开始日常使用，日均检索 Y 次]
- 这个项目成了我面试的主项目，技术深度和工程闭环都能讲

**追问预案**：
- Q：怎么平衡本职和 side project？→ A：前期用周末，原型验证后跟主管沟通，争取了 [需要你补充：如 20% 时间] 正式投入
- Q：如果团队没人用怎么办？→ A：我会先验证是否真的解决痛点。如果用了反馈不好，就砍掉——ADR-006 明确说"所有决策保持可逆"

## STAR 讲述技巧

1. **时间分配**：S 20% + T 10% + A 50% + R 20%。Action 是重点
2. **量化结果**：尽量给数字。没有精确数字给范围（如"重复率从约 40% 降到 5%"）
3. **第一人称**："我做了 X"，不是"我们做了 X"。除非真是团队协作
4. **不贬低他人**：案例 4 讲冲突时，对方诉求是合理的，只是方案不对
5. **有反思**：每个案例结尾讲一句"这次让我学到..."，体现成长性
6. **2 分钟内讲完**：超过 2 分钟面试官会走神。练习时计时
