## 一、13 段必背话术（纯应答项）

### 1. 四级相似度阈值怎么定的？【P0-6 已标定】

**触发**：`阈值 0.85/0.72/0.60 是怎么定的？`

> "我做了标定（`tests/eval/threshold_calibration.py`）：收集三类摘要对的 BGE-M3 相似度分布——同一知识的 LLM 同义改写（应 merge）、同类不同记忆（不该 merge）、异类（应 new）。结果：同义改写对相似度 0.84-0.97（p25 0.878），同类不同记忆上限只有 0.79——**旧值 0.92 高到一半该 merge 的同义对被漏成冲突检测**，'merge 不触发'的担忧被证实。0.85 是自然分离点（高于同类上限、低于同义下界），我把 MERGE 0.92→0.85、CONFLICT 0.75→0.72（跟随下移）。改后同一知识被不同来源写入时能正确合并。边界：8 对改写样本小，真实生产的重复摘要分布待部署后确认。"

**锚点**：三类分布（同义 0.84-0.97 / 同类 ≤0.79 / 异类 ≤0.72）→ 0.92 太高一半漏 merge → 分离点 0.85 → 已改 MERGE 0.85 / CONFLICT 0.72 → 生产待确认。

### 2. 前端 bundle 里有 key，认证防谁？【P2-1】

**触发**：`把 key 从 bundle 里抠出来后，你的系统还靠什么防滥用？`

> "这是我清楚的安全短板：单 key 是 ADR-004 无多租户的推论，key 打进前端 bundle 等于公开，而且全站没有任何 API 限流，成本没有上限。生产上我会做三层：网关按 IP+key 做令牌桶限流、服务端签发短期凭证（前端不再持有静态 key）、把 `/api/memory/ingest` 这类重写入路径单独限流。"

**锚点**：单 key 是取舍 → 无限流是漏洞 → 三层方案（限流/短期凭证/重路径单独限流）。

### 3. APP_ENV=test 能关认证？【P2-2】

**触发**：`为什么测试环境绕过不做成注入的依赖，而是靠环境变量？`

> "这是可审计的隐患——测试安全和生产安全共用一个进程级环境变量开关。正确做法是测试用 FastAPI 的 `dependencies_overrides` 或 fixture 注入替代认证，而不是靠环境变量。我承认这是设计问题，不是 feature。"

**锚点**：共用开关 → 应改依赖注入 → 承认是设计问题。

---

### 4. webhook 没配 secret 怎么处理？【P2-3】

**触发**：`非 production 且没配 secret 时，webhook 接受无签名请求？`

> "production 是 fail-closed——没配 secret 直接拒绝，这层是对的。但我意识到两个默认值（development + 无 secret）叠加等于裸奔，所以生产部署时 secret 是强制的，不是可选项。"

**锚点**：production fail-closed 正确 → 但默认值叠加是裸奔 → secret 强制。

---

### 5. 为什么两套连接池、没有迁移工具？【P2-6】

**触发**：`为什么有两套连接池？你们的 migration 流程是什么？`

> "双池是驱动差异（asyncpg 和 psycopg 各自需要）的技术债，不是设计——它们互不感知、参数写死。更值得担心的是'每次启动清向量列换维度'：误配 `EMBEDDING_MODEL` 会清空生产向量，这已经超出简化的范畴。正确做法是引入 Alembic 迁移，让 schema 演进可回滚。"

**锚点**：双池是技术债 → 清向量列是危险区 → Alembic 可回滚。

---

### 6. 检索是读操作为什么写库？【P2-7】

**触发**：`检索是读操作，每次 UPDATE decay 不会写放大吗？recall_count 衡量什么？`

> "批量 UPDATE 解决了 N+1 和并发丢计数，但没解决'读路径写状态'和'曝光=价值'这两个根本问题——`recall_count` 记的是'被任意查询返回过'，不是'被用过'，垃圾查询会无差别强化返回的记忆。改进方向是显式确认才记 recall，或异步队列合并写。我承认这是被包装成优点的折中。"

**锚点**：批量 UPDATE 是对的一半 → 曝光≠价值是根本问题 → 显式确认/异步合并。

### 7. 实体归一化可靠吗？【P2-9】

**触发**：`进程重启未完成的归一化会怎样？merge 后旧链接呢？`

> "fire-and-forget 不阻塞写入是有意取舍；但进程重启未完成的归一化就丢了（只能手动重跑脚本），merge 掉实体后 `memory_entities` 里的旧链接永不清除，0.85 阈值也没有准确率测量——这两个是真缺口。方案是周巡检补偿 + 定期 cleanup 脚本，这个我还没实现。"

**锚点**：fire-and-forget 是取舍 → 重启丢任务/旧链接残留/阈值无据是真缺口 → 巡检补偿。

### 8. chat_sync 用在哪？【P2-10】

**触发**：`接口强制每个 provider 都写同步方法，生产谁在调？`

> "生产没有任何调用方，是我为接口对称性加的，真实使用者只有测试。这是过度设计，实际应该删掉，让每个 provider 只维护一套客户端。"

**锚点**：零生产调用 → 为对称性加的 → 应删。

### 9. 检索排序是全局最优吗？【P2-12】

**触发**：`multi-query 并集截断、sparse 先截断再过滤，这些是全局最优吗？`

> "不是——multi-query 并集按插入序截断、sparse 候选先按 id 截断再算 Jaccard、衰减是两阶段窗口（top_k×8），这些都是确定性偏差的边界近似。在万级以下语料影响可忽略，但面试官问'全局最优吗'时我不装。"

**锚点**：三处边界近似 → 小语料无影响 → 承认而非辩护。

### 10. 没有团队怎么保证质量？【P2-13】

**触发**：`一个人写 1300+ 测试，没有 code review，怎么保证质量？`

> "这个项目是一个人的团队，所以我用团队工程的纪律约束自己：ADR 记录每个选型为什么、CI 把关每个提交、评估集量化每次检索改动。我承认这替代不了真实的 code review——review 能发现的跨模块问题和视角盲区，是这个项目最大的风险敞口。"

**锚点**：工程纪律替代 review（ADR/CI/评估集）→ 承认替代不了 → 风险敞口是跨模块视角。

### 11. 数据量这么小有意义吗？【P2-14】

**触发**：`70 条记忆、QPS 个位数，这个规模能说明什么？`

> "这个量级足够支撑技术决策——万级记忆库 pgvector HNSW 完全够用，性能瓶颈远未到来，这是拐点思维。但我诚实地讲，生产级规模我没跑过，这是评估的上限。"

**锚点**：拐点思维（万级够用）→ 诚实承认生产级未跑过。

### 12. 为什么不用 LangChain Agent？【P2-15】

**触发**：`为什么不用 LangChain Agent？公司已有 LangChain 基础设施怎么办？`

> "黑盒 + HITL 控制弱 + 调试代价。如果公司已有 LangChain 基础设施——框架只是薄封装，核心价值在记忆/检索/韧性层，迁移不改这些。LangGraph 的价值在 interrupt/checkpoint/流式，超出这三点就回归普通编排。"

**锚点**：三个理由 → 框架是薄封装（迁移无损）→ LangGraph 的价值边界。

### 13. 你的评估是不是有水分？【P2-16】

**触发**：`Recall@5=1.0 是自证吧？数字可信吗？`

> "task completed=0.5 和 unexpected_rate=0.375（DeepSeek 过度调工具）是我最有价值的发现——它比任何完美数字都证明我懂 Agent 的生产行为。主评估集 1.0 是自证的假满分，我主动把它拆成确定性基线和自证通道分开讲，就是因为我做过诚实的评估。"

**锚点**：最可信的数字是难看的那个 → 主动拆开自证通道 → 诚实评估的姿态。

## 二、补充必背（高危追问，代码项已修但口径必须同步）

### 14. 评估数字 1.0 是自证吧？【P0-1】

> "早期 Recall@5=1.0 是 30 条种子语料上的自评结果，query 从种子记忆手工标注、每条只标一条相关记忆，含金量有限——我后来把它定位为回归基线而不是能力上限，并把评估集扩充到 70 条（5 类 × 14、hard 占 30%，语料和 query 都翻倍）。生产 memory 路径**默认确定性基线**现在 0.886/0.767（纯子串匹配，70 条语料上 8 条 miss）；语义通道是显式 opt-in（用被评测模型自评所以非默认）。真实判别力看 27 条 hard-negative：纯向量综合通过仅 59.3%，已用 bounded cross-encoder top-3 重排提到 81.5%。"

### 15. LLM judge 可信吗？【P0-3】

> "judge 用独立 provider 是强制的（避免被测模型给自己打分），但 judge 本身有个已知误判（ans-006 把允许改写当耳边风判 grounded=false），我把它记为 known_anomaly。LLM-judge 的 groundedness 是参考值不是绝对值——deterministic judge 才是门禁。"

### 16. 单次跑的数字能代表能力吗？【P0-4】

> "LLM 行为方差大是真实挑战，我测过同一天跑两次 relation_recall 从 0.53 掉到 0.34。所以门禁不能拿单次采样当能力——要用多次均值 ± 置信区间判红。单次采样当能力指标是会骗人的。"

### 17. 衰减公式和"沉底"卖点对得上吗？【P0-7 通用口径】

> "这些被追问时我主动分级：哪几个是有意取舍（rerank 关闭有 A/B 数字撑腰）、哪几个我后来用数据补上了（四级阈值已标定 0.85/0.72、衰减系数已按 A/B 校准 S=12+floor 0.1）、哪几个仍是边界（真实生产的重复摘要分布待部署后确认）——主动分级比被发现漏强。"

### 18. 对话延迟和成本是多少？【P0-9 实测口径 + 已锁死重排】

**触发**：`你的对话端到端延迟多少？一次对话花多少钱？`

> "我用 `measure_chat_p95.py` 跑了 10 轮真实对话（真实 DeepSeek + 本地 BGE-M3 + 完整检索路径），端到端 P95 73.6s、平均 35.9s。这个数字难看但我如实讲——主要耗时在 LLM 重排：每轮对话要跑约 19 次 `rerank_llm`、加起来约 40s，这是模型被工具 schema 允许自主把 `use_llm_rerank=True` 传给检索工具导致的。我做了三件事：① 从三个检索工具的 schema 移除 `use_llm_rerank` 参数（模型无法再自主开）；② 用 task_eval 验证移除后任务完成率 0.500 持平、答案 groundedness 1.000 不变（检索质量 eval 早已证明 rerank 不改 recall@5）；③ P95 预期降到大半。成本上 10 轮合计 285.9k tokens、估算 $0.081（约 ¥0.06/轮），大头本来是 rerank_llm（75.6k），锁死后只剩 agent_chat（含 cache_read 折扣价）。"

**锚点**：P95 73.6s 难看但真实 → 根因是模型自主开 LLM rerank（19 次/轮 ≈ 40s）→ 已从工具 schema 锁死 + task_eval 验证质量不掉 → P95 预期大降 → ¥0.06/轮 成本可控（cache_read 折扣）。

### 19. 衰减 A/B 和 LLM rerank vs CE 结果是什么？【A/B 实测口径】

**触发**：`记忆衰减加权有用吗？` / `你对比过 rerank 吗？效果如何？`

> "两个都是实测的。**LLM rerank vs bounded cross-encoder** 在生产 memory 路径上：recall@5 完全一样（0.900）——rerank 不改变召回集合；MRR 从 0.819 微升到 0.833（+0.014），但平均延迟从 2.5s 涨到 14.1s（5.5x，每候选一次 LLM 调用）。结论：小语料下 rerank 只微调排序、不救召回，收益 scale-dependent——和之前 hybrid 路径 cross-encoder 有害（0.967 vs 1.000）的结论一致。**衰减我做了完整的 A/B + 调参闭环**：原公式 `S=1+2·recall` 半衰期太短，合成老化分布下 recall@5 从 0.900 掉到 0.367（19/30 目标被压出 top-5）。我把 S 乘数调到 12、加 0.10 保留 floor，同分布重测 **recall 回升到 0.667、MRR 0.622**（被压出目标降到约 10 条），保留排序偏好（29/30 排序仍变）。代价：decay 仍低于无衰减是'过时沉底'的有意取舍。整个调整是数据驱动的——先测出问题、再调参、再 A/B 验证。"

**锚点**：LLM rerank：recall 同 0.900 / MRR +0.014 / 延迟 5.5x → 小语料只微调排序不救召回；衰减：0.367→0.667（调 S=12 + floor 0.1）→ 从「埋掉一半旧记忆」降到「埋掉少数极冷记忆」→ 调参闭环有数据。
